# Proactive Advisor 2.0 验证报告

## 运行范围

- [仓库与版本基线](baseline.md) 在清洁的 `142b51e` 上跑完原有 15 项测试。
- [Linux 测试原始日志](evidence/linux-tests.txt) 收录 Python 3.12 的 44 项检查。43 项通过，原生 Windows 脚本用例在 Linux 跳过。另跑了新增模块与原有组件的 `compileall`。
- [GitHub CI 初始 Windows 失败](https://github.com/tjt253856563-glitch/proactive-advisor/actions/runs/44929590046) 实际跑到了 PowerShell 安装演示。Windows 启动器挑了测试矩阵以外的 Python，新版移除了旧路径 API。已改用跨版本路径校验与 PATH 上的解释器。
- [兼容性修复后的四项 CI](https://github.com/tjt253856563-glitch/proactive-advisor/actions/runs/44930058526) 在 Windows/Ubuntu 和 Python 3.10/3.12 均通过。Windows 结果来自 GitHub 托管环境。
- [回归修复与验收自动推进 CI](https://github.com/tjt253856563-glitch/proactive-advisor/actions/runs/44930432886) 四项矩阵均通过。

## 真实修复演示

[确定性 CLI 轨迹](evidence/offline-repair-trace.json) 保存了进程、退出码、完整断言、文件差异、验证事件和经验关系。最初的加法测试报 `AssertionError: 2 != 4`。编辑仅将 `return a - b` 改成 `return a + b`。加法与标签测试从各自进程返回 0，测试文件哈希保持一致。SQLite 把该次修复关联到最初的失败与最后的验收。

## 真实模型对照

A 和 B 使用相同模型、初始文件与可调用检查；各用独立工作区和数据库，固定随机种子打乱组别。A 使用基础规划与相同执行边界。B 增加 v1.2 规则、自动纠错和可配置验收自动推进。结果记录规则已供应到模型请求、提案、写入、进程启动、退出和独立验收。收到模型响应可核实该次交换，无法看到模型内部是否遵循了每条规则。独立评分在另一目录中用保留用例检查结果，诊断题还检查提交的故障描述。一个精确字符串用例的通过范围只覆盖本数据。

真实模型均在本次临时 Linux 环境用 llama.cpp CPU 推理，权重来自公开 Qwen GGUF 仓库。模型 SHA-256、服务构建号、调用次数、Token 与耗时在各报告内。试验期间存在其他验收负载，计时用于记录和排查。每个 repeat 使用同样的确定性采样配置，样本高度相关。

| 步骤 | 数据 | 观察 |
| --- | --- | --- |
| 1.5B 首轮，三场景各两组 | [全部 12 次](evidence/real-model-pilot.json) | A、B 独立验收均 0/6。记录了重复读取、无效 JSON、遗漏必需检查和无法匹配的替换片段 |
| 1.5B 重测，三场景各两组 | [全部 12 次](evidence/real-model-retest-1.5b.json) | A、B 独立验收均 0/6。A 有两次报告本地目标完成但诊断描述未通过独立评分。B 两次正确识别减法，同时错误地改动原有标签，均触发回归回滚 |
| 3B 修复先导 | [两组完整指标](evidence/real-model-pilot-3b.json) | A、B 均写出正确源文件并通过独立文件与保留用例验收。两组重复请求已应用编辑，目标状态均为 BLOCKED |
| 3B 成功闭环 | [完整配对](evidence/real-model-repair-3b.json) · [失败日志、修复和独立验收](evidence/real-repair-trace.json) | A、B 源码均通过独立验收。A 写对文件后重复编辑并进入 BLOCKED。B 先复现失败，经一次修复后整体 COMPLETED，同时保护了标签 |
| 1.5B 有界回滚复测 | [完整配对](evidence/real-model-rollback-1.5b.json) | A 和 B 均未通过。B 三次提案破坏标签，均回滚；据此增加对已试过补丁的去重 |
| 1.5B 去重复测 | [完整配对](evidence/real-model-dedup-1.5b.json) | A 和 B 均未通过。B 的同一候选实际写入一次，另两次拒绝执行；测试进程从 15 次降为 7 次，源文件恢复至初始字节 |

3B 成功案例的 `sum` 事件 24 记录退出码 1，事件 39 重测退出码 0，事件 44 记录标签测试退出码 0。差异限于 `calculator.py`，独立验收覆盖负数、零和不同输入。A 有一次正确源文件修改和一次已返回的测试。B 有一次正确写入、七次测试进程和两项重复同类命令。该次 A 的输入/输出为 2331/371 tokens，B 为 3524/401 tokens。B 在此例给出可核对的完成状态和错误修复链，代价是更长的上下文和更多测试。更广泛的模型可靠性和相对收益尚未建立。

## 环境未覆盖项

| 环境或能力 | 状态 |
| --- | --- |
| Ollama 适配器 | 真实 loopback HTTP 请求与模拟协议响应通过。用户 Ollama 本机推理 NOT_RUN |
| Codex 适配器 | 已核查此环境 CLI 参数。进程初始化因只读配置环境 BLOCKED |
| 用户的 Windows 11、RTX 5070 Ti、其他项目和真实设备 | NOT_RUN |
| 长期调度与自动生成回归测试 | 未验收。当前提供手动、排队、单次时限、依赖调度及恢复 |

优先级从高到低为目标机器 Ollama 真跑、不同项目上冻结用例的重复对照、原生 Windows 强隔离适配，最后才是长期调度或自动生成回归测试。
