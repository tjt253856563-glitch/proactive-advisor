根据你此前提供的配置：

### 为什么不建议直接运行 32B 模型？

12GB 显存无法将常见的 32B 量化模型及其较大的 KV Cache 全部放进显存。

虽然能够通过内存卸载运行，但你只有 16GB 系统内存，复杂 Agent 任务可能出现明显的性能下降。

而且：

**Agent 的质量不只取决于模型参数，还取决于工具调用的可靠性、任务分解能力和反馈机制。**

一个能稳定调用工具的 9B 模型，有时比一个反复调用失败的 32B 模型更有实际价值。

因此，第一阶段不购买硬件，不租 GPU。


这种启动方式。

但有一个重要问题：官方建议 OpenCode 使用具有足够上下文长度的模型，相关集成文档提出了 64K 以上的要求。

你的 12GB 显存运行 9B 模型时，较长上下文可能会造成显存压力。

因此，它是首选测试对象，而不是保证成功的方案。:chatgpt-content-reference{index="1"}

### 第二推荐：Continue

GitHub：[Continue](https://github.com/continuedev/continue?utm_source=chatgpt.com)

**它支持通过 System Message Tools 兼容部分原生工具调用能力不足的模型。**

这意味着，在某些情况下，它可以绕过模型原生 Function Calling 不稳定的问题。

考虑到你此前遇到过 Qwen 模型工具调用卡住的问题，我认为 Continue 应当作为重要的备选方案。:chatgpt-content-reference{index="3"}

### 暂时不推荐 OpenHands 作为起点

OpenHands 的自动化能力值得关注，但 Windows 本地部署通常涉及 WSL2 和 Docker。

# 三、真正需要构建的 Agent 架构

我的建议不是让模型直接获得全部电脑权限，而是采用以下结构：

```text
                  用户提出目标
                       │
                       ▼
                 任务规划模块
                       │
                生成 PLAN.md
                       │
                       ▼
                  任务执行模块
                       │
           ┌───────────┼───────────┐
           ▼           ▼           ▼
         文件工具     Shell工具    Git工具
           │           │           │
           └───────────┼───────────┘
                       │
                       ▼
                  自动验收模块
                       │
                 ┌─────┴─────┐
                 │           │
                通过        失败
                 │           │
                 ▼           ▼
              完成报告     错误分析
                             │
                             ▼
                         尝试修复
                             │
                             ▼
                         重新验收
```

这里最重要的是：

**规划、执行、验收不能完全依赖模型自己说了算。**

举个例子：

你让 Agent 开发一个 TXT 文件整理程序。

它需要：

1. 生成实施计划。
2. 创建 Python 文件。
3. 编写整理逻辑。
4. 使用测试目录运行程序。
5. 检查输出文件是否符合规则。
6. 如果失败，分析错误并修复。
7. 重新运行测试。
8. 向你报告具体修改和测试结果。

不能仅仅因为模型输出了“任务完成”，就认定程序成功。

# 四、最关键的四项设计

## 1. 文件访问沙箱

你之前希望限制 Agent 只能操作：

```text
D:\AI
```

这个要求应该继续保留。

建议结构：

```text
D:\AI\
│
├── projects\
│   ├── demo-agent\
│   └── other-projects\
│
├── workspace\
│
├── logs\
│
└── backups\
```

不过要特别注意：

**在提示词中告诉模型“只能操作 D:\AI”，并不等于真正实现了安全隔离。**

如果 Agent 拥有完整的 PowerShell 权限，它理论上仍然可能访问其他目录。

因此，真正的隔离需要通过操作系统权限、受限执行环境或独立沙箱实现。

第一阶段建议仅在测试项目目录运行 Agent，并对修改文件和执行命令保留人工确认。重要文件提前备份。

## 2. 自动规划

每次接到较复杂任务时，先生成：

```text
PLAN.md
```

内容包括：

```markdown
# 任务目标

# 已知条件

# 实施步骤

# 验收标准

# 风险与限制

# 当前进度
```

这样能减少模型执行过程中偏离目标的问题。

但不能假定 PLAN.md 能彻底解决上下文遗忘。Agent 仍需要在执行关键步骤前重新读取计划和当前状态。

## 3. 自动验收

我认为这是整个项目最值得投入的部分。

例如任务是：

> 编写一个能自动识别 TXT 小说章节的工具。

我们可以提前设置验收标准：

- 输入文件能够正常读取。
- 中文路径能够正常处理。
- 可以识别指定格式的章节标题。
- 不应丢失原始正文。
- 输入异常时给出合理错误。
- 自动测试全部通过。

随后由程序独立执行测试，而不是让模型凭感觉判断。

这就是从普通聊天机器人走向真正 Agent 的关键变化。

## 4. 失败后的自动修复

建议设置以下规则：

**最多连续自动修复三次。**

每次失败后：

```text
读取错误
    ↓
确定可能原因
    ↓
修改代码
    ↓
重新测试
```

三次仍失败，则停止修改，保留日志和 Git 差异，向你报告原因。

不建议无限重试。

小模型容易陷入重复修改、破坏原本正常代码的循环。

### 第二步：进行原生工具调用测试

在 PowerShell 中运行：

```powershell
@'
import json
import urllib.request

url = "http://127.0.0.1:11434/api/chat"

payload = {
    "model": "qwen3.5:9b",
    "stream": False,
    "messages": [
        {
            "role": "user",
            "content": "请调用工具列出当前目录中的文件。"
        }
    ],
    "tools": [
        {
            "type": "function",
            "function": {
                "name": "list_files",
                "description": "列出当前目录中的文件",
                "parameters": {
                    "type": "object",
                    "properties": {},
                    "required": []
                }
            }
        }
    ]
}

req = urllib.request.Request(
    url,
    data=json.dumps(payload).encode("utf-8"),
    headers={"Content-Type": "application/json"}
)

with urllib.request.urlopen(req, timeout=120) as response:
    result = json.load(response)

print(json.dumps(
    result.get("message", {}),
    ensure_ascii=False,
    indent=2
))
'@ | python -
```

这里的 `list_files` 只是模拟工具，并不会真的读取电脑文件。

**本次测试只检查模型能否正确生成工具调用请求。**

如果输出包含：

```json
"tool_calls"
```

并且里面是 `list_files`，说明模型至少具备生成工具调用的能力。

但这还不能证明它能够稳定完成多步骤 Agent 任务。

如果出现报错，需要先分析 Ollama 版本、模型兼容性及返回格式，而不是立即更换模型。

# 七、第三阶段：加入自主执行机制

当 OpenCode 或 Continue 能稳定完成上述任务时，我们再扩展：

**第一层：自动完成单项任务**

例如整理文件、生成代码、测试程序。

**第二层：自动拆分复杂任务**

例如开发一个简单的 Android 应用，自动生成待办事项并逐项完成。

**第三层：持续检查任务质量**

加入测试报告、错误日志、Git 版本管理和失败恢复。

**第四层：有限自主决策**

当模型发现实现方案存在明显问题时，可以提出替代方案、调整计划，但必须记录修改原因。

涉及删除重要数据、安装未知软件、修改系统设置或对外发送内容等操作时，仍应请求人工批准。

| **OpenCode** | 集成 Ollama，支持文件与命令工具 | 本地小模型可靠性需要测试 | ⭐ 首选 |
| Aider | 代码修改、Git 工作流成熟 | 更偏代码编辑，而非通用 Agent | 备用 |
| Continue | VS Code 集成方便 | 功能与配置方式需要区分 IDE 和 CLI | 可选 |
| OpenHands | 更完整的自主开发环境 | Windows 通常需要 WSL2、Docker，环境更复杂 | 暂缓 |

Aider 已明确支持 Ollama。Continue 的 IDE Agent 模式可以修改文件和执行命令，但要求模型具备相应工具能力。OpenHands 也支持本地模型，不过 Windows 环境部署更加复杂。:chatgpt-content-reference{index="2"}

从你过去的折腾经历来看，现在优先减少环境复杂度更有价值。

## 四、如何真正实现你的目标？

我将项目分成四个阶段。

### 第一阶段：建立最小 Agent

在 Windows 上使用：

```powershell
ollama --version
ollama list
```

确认 Ollama 正常运行。

然后尝试官方支持的启动方式：

```powershell
ollama launch opencode
```

这里有一个需要验证的前提：**你安装的 Ollama 版本可能不支持这个命令。**

如果不支持，就采用 OpenCode 官方文档中的手动配置方式。:chatgpt-content-reference{index="3"}

### 第二阶段：加入你的 Skill

项目目录规划为：

```text
D:\AI\agent-lab
│
├── AGENTS.md
├── SKILL.md
├── PLAN.md
├── goal_check.py
│
├── workspace
│
├── tests
│
└── logs
```

其中：

`AGENTS.md` 用来约束 Agent 的行为。

`SKILL.md` 提供主动审查规则。

`PLAN.md` 定义任务目标和验收条件。

`goal_check.py` 记录测试结果。

但需要确认 OpenCode 能否通过项目级指令稳定加载这些规则。**放入目录不代表自动生效。**

### 第三阶段：验证完整工具链

这是整个项目最重要的一步。

我设计了四个测试：

| 测试 | 任务 | 成功标准 |
|---|---|---|
| 读取测试 | 读取指定 TXT | 内容准确 |
| 修改测试 | 修改指定文件 | 变更符合要求 |
| 执行测试 | 调用 Python 测试命令 | 取得真实执行结果 |
| 自修复测试 | 修复故意设置的程序错误 | 测试从失败变为通过 |

如果第四个测试成功，说明 Agent 已经具备初步的：

**发现问题 → 修改代码 → 验证结果 → 再次修复**

能力。

### 第四阶段：提高自主性

前三阶段通过后，再加入：

1. 多步骤任务规划。
2. Git 版本回退。
3. 失败后的有限重试。
4. 中断后的任务恢复。
5. 任务完成报告。

最终让 Agent 在受控工作区内自主完成一部分开发任务，而不是每一步都等你输入指令。

但系统级操作和其他高风险行为仍然需要授权。

## 七、我的最终判断

你想实现的功能其实分为三个层次：

**第一级：有手有脚。**

Agent 能读取文件、修改文件、执行命令。

这个层次有成熟的开源框架可以实现。

**第二级：有计划，会检查。**

Agent 能根据目标制定步骤，完成后运行测试，失败后尝试修复。

这正是你的 Proactive Advisor Skill 可以发挥作用的地方，但仍需要真实测试工具来支持。

**第三级：长期自主运行。**

Agent 可以跨任务恢复状态，按计划持续执行，管理失败和异常。

这个层次复杂得多，也更容易引入安全和可靠性问题。

**我建议你先实现前两级。**

如果前两级通过，再考虑长期自主运行。而不是还没解决基础工具调用，就加入浏览器自动化、MCP、多 Agent 协作和定时任务。

你目前最大的瓶颈不是缺少新的 Skill，也不是显卡不够强，而是**本地模型与工具执行框架之间的可靠性还没有得到验证**。

下一步最值得做的事情，就是在电脑上建立 `D:\AI\agent-lab`，先让 Qwen3.5 9B 通过上述四项测试。

这一步成功后，你才真正拥有一个可以继续扩展的本地 AI Agent。
